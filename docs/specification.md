# 决策一致性协议（DCP）规范

> 版本：v1.0
> 日期：2026-10-19
> 状态：独立规范。本规范不绑定任何 harness、框架或运行时；文中"宿主"指任何承载多 Agent 的运行环境。
> 来源：由作者个人 AI coding harness 项目中的 DCP 文档（v5）整理而来，已剥离宿主实现细节；协议机制与判据保持不变。
> 缩写：**DCP = Decision Consistency Protocol**（中文名：决策一致性协议）

DCP 解决的是：多个 Agent 并行工作时，如何避免**认知漂移**（各自依据过时或片面的信息行动），同时不为此付出过高的成本。

---

## 0. 范围、假设与非目标

### 0.1 适用范围

- 多个 Agent（或"人 + Agent"）并行工作，存在共享的代码、文档或资源；
- 一个 Agent 的决定可能影响其他 Agent 的后续行动，或约束其他 Agent 的行为；
- 存在一个协调点负责受理升级请求、维护决策日志与版本。

### 0.2 基本假设

| 假设 | 说明 |
|---|---|
| 合作性 | 参与者按协议行事，不以绕过硬门禁为目的。DCP 不是拜占庭容错协议 |
| 单一协调点 | 升级请求汇聚到同一协调者，由它串行定序、递增版本；多平级协调者需另行引入共识或逻辑时钟 |
| 可拦截的写路径 | 宿主的写类操作经过统一执行入口，执行层能拿到调用者依据的版本与记录，且该依据由运行时注入 |
| 最终可达 | 消息可能延迟，但最终可送达；广播丢失由版本门禁兜底，不作为正确性前提 |
| 安全点可判定 | Agent 循环能在两次工具调用之间响应协调消息 |

### 0.3 非目标

- **不做分布式共识**：不解决多主节点之间的日志一致性，也不替代 Paxos/Raft；
- **不做安全隔离**：执行层门禁是政策守卫。若模型能绕过统一执行入口（直接调用底层 API、动态构造命令等），门禁拦不住——这属于宿主的沙箱与权限问题，不属于 DCP；
- **不做实时同步聊天**：会议是异步状态机推进，不是所有人同时在线讨论；
- **不保证"该产生新版本而没产生"能被发现**：门禁只能拦"依据已过期的写"，无法自动发现"某个议题本该升级却被降级"。该盲区见 §11.3，协议不宣称已兜底。

## 1. 设计目标

- 提升**决策质量**与**全局一致性**（防止并行 Worker 之间的认知漂移）；
- 控制**成本**：不是所有问题都值得开会。

会议是"用时间和 token 买决策质量"的机制。因此协议的重点不在于让会议更快，而在于**让不该开的会根本不开**。

---

## 2. 五级升级阶梯（L0–L4）

排序轴为**承诺强度**（无承诺 → 单点承诺 → 全局约定 → 多方决议），而非"影响范围"。原因是"影响"不可观测：一个答案是否影响别人，往往在得到答案之后才知道；而"这个答案会不会被引用为别人依赖或遵守的东西"在提问时就能判断，并且能在门禁上检验（见 §2.2）。成本为伴随属性。

先定义两个词：

> **影响** = 对他人责任域的写，或对他人行为的约束。知道关于别人的事，不算影响。
>
> **承诺** = 一个可以被他人依赖、并作为后续行为依据的答复或决定。按"约束谁"分档：不约束任何人（L1）→ 只约束某个责任域（L2）→ 约束所有相关 Worker（L3）→ 由多方共同作出（L4）。

| 层级 | 名称 | 触发条件（承诺强度） | 决策者 | 处理方式 | 记录与可引用性 | 成本 |
|---|---|---|---|---|---|---|
| **L0** | 自决 | 不需要本上下文之外的信息，也不产生对外承诺 | Worker | 自行决策 | 无记录 | 极低 |
| **L1** | 信息 | 需要外部事实，但**不产生承诺**；答错只误导提问者，不约束他人行为 | 记录 / 主控 / 用户 / 知情者 | 直接答复或检索；不广播、不递增版本 | 轻量记录；**不可引用为依据** | 低 |
| **L2** | 单点承诺 | 由某个责任域 owner 作出**可被依赖的承诺 / 确认**，但不改变全局约定 | 责任域 owner（主控配对） | 主控配对后双向问答；不递增版本 | 咨询记录：`OwnerId` + `Binding=true` + `BasisVersion`；**可引用为依据** | 中 |
| **L3** | 全局约定 | 改变其他 Worker 必须遵守的约定 | 主控 | 裁决 + 广播 + 决策日志版本递增 | 版本化决议；可引用，需版本校验 | 中高 |
| **L4** | 多方决议 | 无唯一 owner、存在互斥方案、争议或需多方共同评估 | 会议（主控仲裁） | 组织会议；决议写日志 + 广播 | 版本化决议；可引用 | 高 |

排序直观：自己 → 查 / 问事实 → 让 owner 承诺 → 改写全局约定 → 多方共同决定。**排的是承诺强度，不是参与人数，也不是纯 token 成本。** L2 与 L3 之间仍可能出现成本小倒挂（多轮问答未必比"裁决 + 广播"便宜），但 L3 改的是全局状态，权重更高。

### 2.1 判定树（四问）

```
① 需要超出我上下文的信息吗？
   否 → L0
   是 → ②
② 这个答案会被写进代码 / 文档，成为别人以后要依赖或遵守的东西吗？
   否 → L1（信息）
   是 → ③
③ 它要求所有相关 Worker 都遵守，还是只约束我与某个责任人之间？
   全局 → L3
   只在两者之间 → ④
④ 找不到唯一 owner，或存在互斥方案 / 争议？
   是 → L4
   否 → L2（单点承诺）
```

四条补充说明：

- ① 的"信息"包括既有记录、代码、文档、主控、用户与知情者；能查到的不必问人。
- ② 的"依赖 / 遵守"包括：写进代码作为契约、写进文档作为约定、作为后续写操作的依据。仅仅是"知道了某件事"不算。
- ③ 的"全局"指要求所有相关 Worker 遵守；"仅两者之间"指只在提问者与该责任域 owner 之间成立。
- ④ 只作用于 L2 分支。L3 若方案不唯一或需要多方评估，按 §3 白名单转 L4——白名单与阶梯仍是两个正交维度（§3）。

**事实必须由某个 Worker 在安全点回答时**：即使它不产生承诺（②判"否"），也走 §15 的咨询通道，但记录标 `Binding=false`、不可引用；分类仍是 L1，通道借用 L2。这样"分类"与"通道"各自只有一个判断依据。

### 2.2 可引用性：让边界在门禁上可执行

L1 与 L2 的真正差别不能只是"问谁"，否则判错了也没有后果。本协议把差别落在**可引用性**上：

| 记录 | 产生于 | 可作为写操作的依据 | 参与版本校验 |
|---|---|---|---|
| L1 信息记录 | L1 | **否** | 否 |
| L2 承诺记录 | L2 | **是**（需 `Binding=true`、`OwnerId` 非空、`BasisVersion` 与当前决议一致） | 记录本身不递增版本；引用它的写操作仍按其 `BasisVersion` 校验 |
| L3 / L4 决议 | L3 / L4 | 是 | 是 |

门禁规则：在版本校验之外增加**依据类型校验**——写操作若声明依据为咨询记录，该记录必须 `Binding=true` 且 `OwnerId` 非空；引用 L1 记录一律拒绝，并要求把该问题重分类为 L2 后重新取得承诺。跨责任域的写操作（由责任人登记判定）必须声明依据；本域内的写操作可以只做版本校验。

这条规则的作用不是增加一次检查，而是**把"L1/L2 判错"从无声漂移变成一次可计数的门禁拦截**：如果主控把一个本该是承诺的问题当成 L1，问题方一旦拿它当写依据，门禁就会拦下；如果没拿它当依据，那这次误判本来也没有治理后果。

**分类是暂定的，答复时可重分类**：

- 责任人答复"这只是事实" → 降为 L1（记录标 `ReclassifiedFrom=L2`）；
- 答复引出约定变更 → 升为 L3（记录标 `ReclassifiedFrom=L2`，并由主控广播 + 递增版本）；
- 提问者认为答复会被依赖 → 可申请升为 L2 并补承诺记录。

每次重分类都要留原层级、新层级与理由，作为 L1/L2 触发率测试的数据（§15.7）。

**默认规则（一条就能覆盖大多数情形）**：凡是要写进别人责任域、或要引用别人答复作为依据的，至少 L2；其余一律 L1。不确定时不要默认开会，也不要默认 L1——按"是否会被引用"这一条判。

### 2.3 场景卡

| 场景 | 判定 | 理由 |
|---|---|---|
| A 问 B 模块空输入返回 null 还是抛异常 | **L1** | 纯事实，不产生承诺 |
| A 要依赖这个行为长期不变 | **L2** | 需要 B 的 owner 作出稳定性承诺 |
| A 问"我能把 `Foo()` 的签名改了吗" | **L3** | 答案本身改变约定 |
| A 问"你这轮会改 `Foo` 吗" | **L2** | 意图协调，产生单点承诺，不改约定 |
| A 问"项目里有没有现成重试工具" | **L1**（或 L0） | 查记录即可，不必问人 |
| A 问"日志用 JSON 还是文本" | **L4** | 多方案、影响多方 |
| A 问"你负责的模块能接受我传 null 吗" | **L2** | owner 的单点确认 |
| A 只是阅读 B 的实现细节 | **L1** | 阅读不产生承诺；写进代码依赖它才升 L2 |

### 2.4 收缩规则与备选

L2 是暂定层级，须先经触发率前置测试（§15.7）验证。测试后若发现 L2 几乎只承载"事实转交"而没有真正的承诺，**收缩不是删除 L2，而是把 L1/L2 合并为一级咨询**，用记录上的 `Binding` 字段区分事实与承诺；编号随之收缩为 L0–L3。若测试发现承诺类议题确实存在且需要独立的责任人路由，则保留五级。

> 不把 L1/L2 直接合并的理由：**承诺强度是治理轴，且可被门禁检验**。合并后"这条记录能不能作为写依据"仍要一个字段来表达，只是把层级问题换成了字段问题；在承诺类议题占比未测之前，保留两级更容易观察分布。L2 的完整设计见 §15。

## 3. 议题白名单

只有以下类型的问题有资格升级到 L4：

| 议题类型 | 说明 |
|---|---|
| 接口 / 契约变更 | 改变了其他 Worker 必须遵守的约定，且方案不唯一 |
| 方案选型 | 存在多个互斥可行方案，且影响面大 |
| 冲突裁决 | 两个 Worker 的工作相互矛盾 |
| 影响面评估 | 改动波及多个模块，需要共同评估 |

白名单之外的问题一律走 L0、L1、L2 或 L3。

**白名单与阶梯是两个正交维度**：白名单判断"有没有资格升级到 L4"，阶梯判断"该升到哪一级"。

## 4. 会议状态机

```
IDLE
  │ Worker 发起请求
  ▼
REQUESTED ──── 议题不在白名单 ──→ 退回 L3
  │
  ▼
PENDING_APPROVAL ──── 用户拒绝 / 超时 ──→ 退回 L3
  │ 用户同意
  ▼
CONVENING   （发出参会通知，等待各参会者到达安全点）
  │ 全员到齐 / 超时降级
  ▼
IN_SESSION  （陈述议题 → 各自出方案 → 仲裁）
  │
  ▼
CLOSED      （决议写入决策日志，打里程碑，广播）
```

## 5. 人类门禁与审批转交

- 会议发起前必须获得用户授权；
- 界面（或任何通知渠道）弹出审批卡片，展示：议题摘要、参会者列表、预计 token 成本；
- **超时策略**：默认 120 秒无响应视为拒绝，发起者退回 L3 处理；
- 待审批请求进入队列，不阻塞 Worker 的其他工作；
- **L1 的用户提问通道**：L1 的信息无法从记录、代码或主控取得时，可直接向用户提问，走同一个待答队列，但不占用会议资源。所有需要用户介入的请求（会议审批、L1 提问、危险操作确认、决议审核）应在界面上统一处理；
- **审批转交（前瞻）**：在多级协调结构（例如 Sub 主控）中，下级协调者的审批请求默认由上级处理；触及必须上交条件时，才转交给真实用户。转交时保留完整的请求来源链路，用户看到的是"谁在什么背景下请求什么"；
- **介入点的开关控制**：本节描述的是默认行为（批准开会 + 审核决议都需人工）。是否免去其中之一，由 §13 信任授权的两个开关控制。

## 6. 安全点

**定义**：一次工具调用返回之后、下一次工具调用发起之前。

规则：

- Worker **只在安全点**检查消息邮箱、响应会议邀请；
- **绝不中断进行中的操作**（文件写到一半、命令执行中）；
- 最坏等待时间 = 单次工具调用的耗时，可预测。

---

## 7. 会合、超时与缺席

会议不是即时对话，而是**状态机推进**——参会者可能正在执行长任务，不可能立刻响应。

| 情况 | 处理 |
|---|---|
| 全员到达安全点 | 会议开始 |
| 个别 Worker 超时（默认 60 秒） | 记为"缺席"，会议照常进行 |
| 缺席者 | 会后接收决议，视为已对齐 |
| Worker 卡在超长命令 | 用户可手动强制中断（危险操作，需二次确认） |

**实现方式**：主控维护一个"待参会集合"，在自身的调度循环里检查各参会者是否已到达安全点——**不需要独立的同步原语**。

**为什么不能省掉这一节**：等待、超时、缺席三者是**异步参与的必然代价**。Worker 不能被打断（见 §6 安全点），主控面对一个正在跑长命令的参会者，只有两种选择——等（需要超时机制）或不等（需要缺席定义）。这不是可以设计掉的复杂度。

> **前提与分档（人控模式）**：本节的超时与缺席，前提是"参会者是 Agent、等待有界"。当决策者为人（人控模式，见 §13.8）时等待无界，按层分档：**L1 的主控 / 用户直答、L3、L4 不超时回落，只能挂起**，等待答复或由用户显式取消（L3 / L4 之上没有更高层级可回退）；**L1 的事实转交与 L2 的 peer（责任域 owner）应答保留超时与缺席**，超时即回落 L3。这条只作用于决策者为人时；自动模式下 L1 / L3 / L4 仍按本节既有超时处理。

## 8. 会议排队与定序

- 同一时刻**只允许一场会议**：主控持有当前会议引用，非空时新请求进入等待队列；
- **排序依据：主控的单点接收序号**（单调递增计数器），先到先处理。

**为什么不需要逻辑时钟**：所有升级与会议请求仍汇聚到主控这一个节点，主控的接收顺序本身就是一个确定的全序——而这正是 Lamport 逻辑时钟想要算出来的东西。引入 L1 事实转交与 L2 后，升级请求的全序不变，且 **L1 / L2 都不产生版本号，因此无需定序**；逻辑时钟的前提（"顺序需由多个节点协商确定"）仍不成立。

**为什么不需要死锁防护**：L1 的事实转交与 L2 都可能引入 Worker 之间的互相等待，但二者都是 **1:1（单对单）+ 非阻塞（仅在安全点应答）+ 禁止嵌套**（同一时刻一个 Worker 只处于一个咨询会话，咨询内不得再发起咨询），使**等待图深度 ≤ 1，构不成循环等待环**。原"两个 Worker 互相等对方同意"的会议场景仍不存在——会议发起只需主控受理与用户批准，不需要其他 Worker 同意。

> **扩展注记**：若未来出现多个**平级**主控节点，单一接收点将消失，届时需重新引入逻辑时钟或共识机制。若采用派生式的层级协调节点（各自维护自己的序号），层级之间无需全局定序。

## 9. 会议流程

1. 发起者陈述议题；
2. 各参会者**独立**给出方案（并行生成，互不可见，避免相互锚定）；
3. 发起者汇总方案；
4. 主控仲裁，产出决议；
5. 决议写入决策日志、打里程碑标记，并**广播给全部 Worker**（所有 Worker 均订阅结论）；
6. 所有参会 Worker 恢复工作。

## 10. 结论订阅

所有 Worker 通过**订阅结论**保持全局同步——这是防止认知漂移的基础保障。

| 项 | 设计 |
|---|---|
| 模式 | 仅订阅结论：只接收决议摘要，不接收讨论过程 |
| 范围 | **全部 Worker**，不区分相关性 |
| 时机 | 决议写入决策日志后立即推送 |
| 冲突处理 | 订阅者若发现结论与自身判断或既有工作冲突，**走正常升级通道重新提出**（L3 或 L4），由主控重新裁决 |

**不设"举手"机制，也不设"全程旁听"。** 订阅者本就拥有完整的升级通道，与结论不一致时走该通道即可——用已有机制覆盖新需求，避免协议膨胀。推送内容只是决议摘要，全量推送成本可控；真正昂贵的讨论过程从不外发。

## 11. 决策日志与版本硬门禁

L3 的广播与 L4 的决议都写入决策日志。广播是"通知"，不是"约束"——真正的防漂移机制是**版本校验**。

### 11.1 决策日志

由主控维护，每条决议包含：ID、议题键、版本号、时间戳、议题、结论、参会者、异议记录、关联里程碑。

### 11.2 版本校验是执行层的硬门禁

**这不是提示词里的软约定。** 这一点很关键：如果只在系统提示词里写一句"记得检查决议版本"，模型完全可以不检查就直接写入——那样它就配不上"绕不过去"这四个字。

| 环节 | 做法 |
|---|---|
| 记录依据 | 每次工具调用携带该 Agent 当前依据的决议版本与依据 ID（由运行时注入，不依赖模型自觉） |
| 拦截点 | 执行层在**写类操作**（写入 / 删除 / 执行命令）执行前拦截 |
| 依据类型 | 若依据是咨询记录，必须 `Binding=true` 且 `OwnerId` 非空；L1 信息记录一律拒绝（§2.2） |
| 判定 | 比对依据版本与决策日志当前版本 |
| 过期处理 | **拒绝执行**，将差异回灌给该 Agent，要求重新对齐后再试 |
| 只读操作 | 不拦截（读操作不会造成漂移） |

这样版本校验就落在宿主的代码路径上，而不是模型的行为习惯上。这是分布式系统中防"陈旧读"的标准做法：广播可能漏（Worker 当时正在跑长命令），但代码级的拦截绕不过去。

> **边界声明**：只有当宿主的写类操作**全部**经过统一执行入口时，这条才成立。若存在绕过路径，门禁退化为政策守卫，不能宣称"绕不过去"。宿主必须如实声明自己的覆盖范围。

### 11.3 硬门禁的边界：判定可审计性

版本门禁只能防**"依据过期的写"**，防不了**"该产生新版本而没产生"**；§2.2 新增的依据类型校验能补上一部分，但不是全部。

门禁的判定者与判定的错误仍是同一个主体：分类由主控单方做出。四问判定树（§2.1）把判定点变成四个，**误判面因此变宽**：

- 一旦主控把 L3 议题误判为 L1 或 L2：不广播、不写决策日志、版本号不变；
- 受影响方无从得知自己已被影响——§10 的订阅机制在这里失效，因为压根没有推送；
- 门禁对"没有版本号的误判"仍然无感；它只在问题方**引用**了错误依据时才拦得下。

但可引用性把几类误判分开处理了：

| 误判 | 是否可发现 | 后果 |
|---|---|---|
| L1 判成 L2 | 可观察 | 多一次咨询，成本增加，不产生漂移（保守方向） |
| **L2 判成 L1** | **可发现（若被引用）** | 引用 L1 记录的写操作被门禁拒绝；若从未被引用，则本来也没有治理后果 |
| **L3 判成 L2** | **不可发现** | 承诺记录可被引用、又不广播，受影响方仍不知道约定变了——**本协议最大的残余盲区** |
| L3 判成 L1 | 部分可发现 | 被引用时拒绝；但约定本身仍未广播 |
| L3 判成 L4 | 可观察 | 多开一次会，成本增加（保守方向） |

结论：**审计可见性提高，但兜底没有完成**——L1 与 L2 都留记录，完全无记录的只剩 L0；**L3 → L2 的漏判仍无门禁兜底**，这一点须如实写入，不能因为多了记录就宣称兜底已完成。

兜底措施（都不产生版本号、不参与版本校验）：

| 兜底 | 做法 | 成本 |
|---|---|---|
| L1 信息记录 | 答复落一条轻量记录（时间、提问者、问题摘要、答复摘要），标 `Binding=false`、`Citable=false`。不广播、不递增版本，仅用于事后审计 | 一条记录 |
| L2 承诺记录 | 落咨询记录，带 `OwnerId`、`BasisVersion`、`Binding=true`；可被引用，但不递增版本 | 一条记录 |
| 判定权下放 | 答复回给提问者时附一句"若你认为此答复会被依赖，可申请升为 L2"。提问者比主控更清楚答案会被怎么用 | 一句话 |
| 重分类留痕 | 降级 / 升级都写 `ReclassifiedFrom` 与理由 | 一个字段 |

**为什么"判定权下放"现在更有效**：旧版把"影响他人"作为判据，提问者也无法客观回答；新版只问"这个答复会不会被引用"，提问者在写代码 / 文档时自己就知道。

**这条边界同时是信任授权的前提**：默认状态下人还在回路里兜底，开关打开后人退出回路，L3 → L2 的漏判将完全无人察觉。因此 §13 的开关必须在判定可审计之后再打开。

**适用范围（人控模式）**：人控模式下（见 §13.8）决策者是人，L1 / L2 / L3 / L4 的分类不再由主控单方决定，本节的盲区只作用于**决策者为 Agent** 的模式。

## 12. 成本护栏

| 护栏 | 默认值 |
|---|---|
| 参会人数上限 | 4 |
| 方案轮数上限 | 1 轮方案 + 1 轮仲裁（决议被要求重出时额外消耗一轮；预算已用尽则按否决处理） |
| 单次会议 token 上限 | 可配置 |
| 相同议题去重 | **由主控负责**：受理升级请求时比对决策日志，相似议题直接复用上次决议，不重复开会 |

**去重有与 §11.3 同类的盲区**：相似性判定同样由主控单方做出、同样不产生新版本。若"相似"误判，会复用不相关决议，而复用的版本号本身合法——门禁同样无感。且去重是优化动作，通常不会被怀疑，因此比分类误判更隐蔽。**复用决议时必须留下复用依据**（被复用决议 ID + 判定理由），与咨询记录同处存放，使复用可事后审计。

## 13. 人类介入深度轴

前 12 节解决的是"决议如何产生与升级"。本节解决的是**"人类要介入到什么程度"**——把免批准开关（开关 A）、免审核开关（开关 B）、断路器自动收回、以及人控模式统一表述为**同一条轴上的档位**：开关 A / 开关 B 是这条轴上的两个布尔档位，断路器是轴上的自动回退档（§13.4），人控模式是"拉满"的档位（§13.8）。

### 13.1 两个介入点与两个开关

一次完整的升级请求，人类有两个可能的介入点：

```
Worker 发起升级
   ↓
【批准开会？】              ← 开关 A 控制
   ↓
开会 → 产出决议
   ↓
【审核决议 / 批准执行？】    ← 开关 B 控制
   ↓
执行
```

| 开关 | 控制 | 默认状态 |
|---|---|---|
| **开关 A** | 是否免去"批准开会" | 关闭（即需要批准） |
| **开关 B** | 是否免去"事后审核" | 关闭（即需要审核） |

两个开关**互相独立**，可单独或同时打开。均为**全局开关**，不按议题类型分别配置。

默认状态下人类在两个介入点都在回路里——这是保守的默认值。

两个开关不是并列的独立机制，而是同一条**介入深度轴**上的两个布尔档位；断路器是轴上的自动回退档（§13.4），人控模式是"拉满"档（§13.8）。

### 13.2 人工审核的产物

审核不只是"通过 / 否决"两个动作，它同时产生三样东西：

| 产物 | 用途 |
|---|---|
| 裁决结果 | 决定该决议是否生效 |
| 否决理由标注 | 决策日志的一部分；Agent 自主裁决时的参照示例；后续调提示词的依据 |
| 审核数据 | 判断开关是否该打开的**依据** |

所以人工审核不是"因为 AI 不可信而加的限制"，而是在积累可用于决策的证据。

### 13.3 放开开关的依据

**开关不由审核数据自动触发，只由人显式打开。** 系统基于以下数据给出"是否建议放开"的判断：

| 条件 | 说明 |
|---|---|
| 通过率 ≥ 阈值 | **按议题类型分类统计**，不可全局统计 |
| 严重否决次数 = 0 | 否决理由需分级：风格 / 格式问题为轻微，方向性错误为严重 |
| 由该类决议引发的返工 ≤ 阈值 | 用"认知漂移事件数"衡量（口径见 [设计论证](design-notes.md) §5） |
| 样本量 ≥ 最小值 | 例如至少 20 次人工审核记录；样本不足不给建议 |

**为什么必须分类统计**：简单议题（命名、格式）的通过率会拉高全局数字，掩盖复杂议题上的低通过率。若只看全局数字就打开开关，很可能一放开就在架构议题上翻车。分类统计让"哪类议题还不该放开"可见——即便最终只有一个总开关，这份可见性也是判断的前提。

**为什么通过率是必要但不充分的**：只看通过率会招来指标操纵——Agent 会学会"产出容易被通过的决议"，而不是产出正确的决议。它发现"提保守方案总被通过"，于是所有议题都提保守方案，通过率漂亮但决策质量下降。所以必须叠加"严重否决"与"返工"两个条件。

**放开的前置条件**：判定可审计性（§11.3）必须先就绪。默认状态下人在回路里兜底，L3 → L2 的漏判仍可能被人发现；开关打开后人退出回路，这类误判将完全无人察觉。因此"是否建议放开"还应包含一项检查：**L1 / L2 记录是否在积累、`Binding` 与 `OwnerId` 是否完整、去重的复用依据是否完整**。审计数据不完备之前，只给"暂不建议放开"。

### 13.4 自动收回（断路器）

放开由人决定，但**收回可以自动**。

开关打开后，系统持续用滑窗监控决议质量：**若最近 N 次中出现严重否决或引发返工，自动关闭开关 B（免审核）并提醒用户。** 收回的只可能是开关 B——严重否决与返工都是"决议质量"信号，语义上只指向事后审核；**开关 A（免批准开会）没有自动收回路径**，只能由人手动关。

这样既避免了"系统自动放权"的风险，又保证不会出现"一次放权、永久失控"。

### 13.5 审核质量的保障

如果每个决议都要用户细读并写理由，用户很快会敷衍点通过。此时通过率虚高，数据失真，后续判断全部建立在噪声上。

| 对策 | 做法 |
|---|---|
| 轻量卡片 | 只展示结论、承诺层级、关联里程碑、关键分歧点 |
| 预置理由 | 否决用选项而非自由输入 |
| 批量审核 | 低风险议题支持批量通过 |

**这三条是界面与流程上的对策，不是一个监测指标。** 不建议把"审核疲劳度"作为指标：在小样本场景（如单人开发、少量审核者）下，该指标的样本过少，测出来必然自我否定，反而干扰判断。此处的对策只服务于一件事——让 §13.3 用到的通过率、严重否决次数、返工次数三类数据可信。

### 13.6 与五级升级的关系

两者管不同维度，**正交组合**：

| 机制 | 决定什么 | 是否受开关影响 |
|---|---|---|
| 五级升级（§2） | 议题的**承诺强度**：要不要广播、要不要开会、记录能不能被引用 | 否，这是由判据确定的协议属性 |
| 人类介入深度轴（本节） | 人类的**介入深度**：批准开会 / 审核决议 / 是否由人出任决策者 | 是，由开关与档位控制 |

一个产生全局约定（L3）的议题，即使开关全开也仍要广播——只是决议不再需要人点头。

人控模式（§13.8）是这条介入深度轴上的"拉满"档位，仍属本节维度（决定"人类介入到什么程度"），与 §2 五级升级（决定"议题的承诺强度"）保持正交。

### 13.7 与开发过程的关系

这个机制在落地前就可以先以人工流程试运行：开发者作为审核者，一边验证协议、一边积累记录。**试运行期产生的审核记录直接就是评估开关是否该放开的数据。**

### 13.8 人控模式（轴上的"拉满"档位）

人控模式是**主控 Agent 的基础形态**：主控先按"决策者可以是人"来构建，Agent 自主裁决是其后的升级路径，而不是反过来。它是介入深度轴上"拉满"的档位——用户不只是审批，而是直接扮演主控 / 决策者。

三件与既有设计的关系：

| 项 | 内容 |
|---|---|
| 角色与服务的解耦 | 主控**角色**（决策者，可为人或 Agent）与常驻的**仲裁服务**（决策日志、责任人登记、升级请求队列、单点接收序号、会议状态机）分离。移交只换角色、不动服务，因此决策日志与待答队列不因切换决策者而丢失 |
| 秘书 Agent | 任务组的结构生成与记录角色：分析问题、生成拆分方案、创建 Worker 并登记责任域、全程记录与转发；**不持有任何责任域**，因此不能作为 L2 的承诺主体——指向它的提问只能是 L1 信息或 L3 约定，需要单点承诺时应转交给持有相应责任域的 Worker |
| 拆分确认与移交 | "拆分方案先行确认"属人类门禁（§5 的扩展，可作开关）；"主控身份移交给用户"属运行模式（即 §13.6 轴上的档位）。两者须独立配置，否则"要门禁"与"要移交"无法分别开关 |

人控模式下决策者是人，因此 §11.3 的"主控单方误判"盲区不适用——该盲区只作用于决策者为 Agent 的模式；L1 的主控 / 用户直答、L3、L4 的等待无界，其超时语义按 §7 的分档处理。

## 14. 错误处理（本模块相关）

| 场景 | 处理 |
|---|---|
| 会议无法推进 | 超时机制兜底（见 §7）+ 用户可强制中断卡住的 Worker |
| 写操作被版本门禁拒绝 | 差异回灌给该 Agent，要求重新对齐后再试（见 §11） |

宿主的其他错误处理（进程崩溃、存储故障、网络中断等）不属于本协议，由宿主自行定义。

## 15. 定向咨询（L2：单点承诺）

> L2 是暂定层级，须先经 L2 触发率前置测试（§15.7）验证；若测试判定承诺类议题不足以独立成层，按 §2.4 与 L1 合并为一级咨询（`Binding` 字段区分事实 / 承诺），而不是直接删除。

### 15.1 定位

L2 处理**"由某个责任域 owner 作出可被依赖的承诺 / 确认，但不改变既有约定"**的议题（§2.1 判定树第 ③、④ 问）。位置固定在 L1 与 L3 之间。

- L1 是**信息**：不产生承诺，记录不可引用；
- L2 是**承诺**：owner 以其责任域为范围作出确认，记录可引用；
- L3 是**约定**：承诺的范围扩大到所有相关 Worker，必须版本化 + 广播。

L2 的结论若引出约定变更，**不得自行升级为版本**，必须回流主控走 L3，并记录 `ReclassifiedFrom=L2`。

### 15.2 责任人登记（Ownership Registry）

- 主控（人控模式下由其执行体**秘书 Agent**，见 §13.8）在**派生 Worker 的同一时刻**写入该 Worker 的责任范围（模块 / 接口 / 文件范围）。
- 登记项：`WorkerId`、责任域标识、创建时间、当前决议版本。
- 作用有五：为 L2 提供**承诺主体**（不只是"谁知道"）；为 §12 去重提供"谁受影响"的依据；为 L4 提供参会者筛选依据；**为 Agent 级并行提供写分片依据**——同一时刻一个责任域只由一个 Worker 写入；为门禁的"跨责任域写"判定提供依据。
- **知识归属与承诺权分离**：知道某个事实的 Worker 未必有权代表该责任域作出承诺。L2 要求的是后者；只有前者时按 L1 处理，或由 owner 追认后补一条承诺记录。
- 登记随 Worker 回收而失效，历史条目保留供审计。

### 15.3 协议流程

```
问题方 Worker
  │ ① 发起咨询请求（议题摘要 + 期望责任人 + 拟分类 L1/L2）
  ▼
主控：受理 → 校验（分类、是否与决策日志重复、owner 是否存在）→ 配对 → 留痕
  │ ② 授权建立双向通道
  ▼
责任人 Worker：下一个安全点接受请求
  │ ③ 问题方提问 → 责任人回答（可多轮）
  ▼
  ├─ 回答为"事实澄清" → 记录 Binding=false（分类 L1），结束
  ├─ 回答为"单点承诺" → 记录 Binding=true（分类 L2），结束
  └─ 回答引出"约定变更" → 记录 ReclassifiedFrom=L2 → 上报主控走 L3
```

受理时必须先做一次分类校验：拟分类为 L2 但 owner 不存在 → 退回 L4（或转交主控指定 owner）；拟分类为 L1 但答复会被引用 → 要求升为 L2。分类结果写入记录，答复后可重分类。

### 15.4 必须加的约束

| 约束 | 内容 | 目的 |
|---|---|---|
| 控制面 / 数据面分离 | 咨询的受理、配对、留痕走主控；问答内容 P2P 直连 | 保住"升级请求的单一全序" |
| 版本权威不下放 | 任一 Worker 只能**建议**更新；版本递增与广播由主控执行 | 决策日志保持单一写者 |
| 非阻塞应答 | 责任人仅在安全点应答；超时（建议值可配置）即缺席 | 复用安全点与会合机制的既有约束（§6、§7） |
| 超时回落 | 责任人超时或拒绝 → 提问方回落 L3 | 保证有兜底，不阻塞 |
| 禁止嵌套 | 一个 Worker 同一时刻只处于一个咨询会话；咨询内不得再发起咨询 | 等待图深度 ≤ 1，不成环 |
| 全员可审计 | 每次咨询落一条咨询记录（与 L1 信息记录同处存放），由协调方（秘书 Agent / 主控 Agent）写入控制面；记录必须带 `Binding`、`OwnerId`、`BasisVersion` | 防"私下达成一致"造成漂移 |
| 可引用性 | 只有 `Binding=true` 且 `OwnerId` 非空的记录能作为写依据；L1 记录不可引用 | 让 L1/L2 的边界在门禁上可执行（§2.2） |
| 重分类留痕 | 降级 / 升级都写 `ReclassifiedFrom` 与理由 | 给触发率测试提供数据（§15.7） |

### 15.5 与既有章节的关系

**§8 的两条论证已据此改写**：原"Worker 之间不直接通信，所以不需要逻辑时钟"改为"升级请求仍汇聚主控，全序不变；L1 / L2 都不产生版本号，因此无需定序"；原"Worker 不互相等待，所以不需要死锁防护"改为"L1 的事实转交与 L2 都可能引入互相等待，但二者都受 1:1 + 非阻塞 + 禁止嵌套约束，等待图深度 ≤ 1，构不成环"（见 §8）。§8 的"扩展注记"保留。

L2 记录本身不产生版本号，因此不进入 §11 的版本校验；其咨询记录与 §11.3 的 L1 信息记录同处存放，供事后审计。但 L2 的 `BasisVersion` 仍被记录，用于"承诺作出时依据的决议版本"的追溯；若该决议后来被推翻，**引用这条承诺的写操作**会因依据版本过期被门禁拦下。

### 15.6 状态机增量

Worker 状态机新增两个状态（对应 L2）：

| 状态 | 含义 |
|---|---|
| CONSULT_REQUESTED | 已发起咨询请求，等待主控受理 |
| CONSULTING | 咨询会话进行中（提问方等待应答 / 责任人应答） |

`CONSULTING` 与 L4 的会议状态互斥；进入 `CONSULTING` 仍受安全点约束（§6）。L1 的事实转交复用同一对状态，但记录为 `Binding=false`，且不进入版本校验。

### 15.7 成本、收益与触发率测试

- 收益：压降 L4 触发率；消灭"主控答不出的 L3"；为宿主补入双向通道、并发调度、防成环；为"承诺"提供可引用的依据，减少重复询问。
- 成本：新增一对状态、一条审计记录类型、一套超时 / 回落逻辑；责任人登记与角色系统耦合。
- 边界：不能替代 L4 的争议型 / 多方型议题；**先做 L2，再观察 L4 剩余触发率**。
- **触发率测试（前置）**：从真实开发对话中取 20–30 个"当时不知道该问谁"的问题，做成场景卡（§2.3 是种子集），逐张标注分类、`Binding`、`OwnerId`、是否被引用。统计三件事：
  1. L1 / L2 各自占比；
  2. L2 中 `Binding=true` 的比例——若接近 0，说明 L2 只承载事实转交，应按 §2.4 合并；
  3. **L1 记录被引用为写依据的次数——应为 0**；非 0 即分类错误，需重分类并计入门禁拦截。
- 成本口径：L2 与 L3 之间可能存在成本小倒挂（见 §2），报告中据实说明。

### 15.8 验收

- 一次完整 L2 会话可在模拟环境中跑通：正常承诺、事实澄清降级 L1、责任人超时回落 L3、咨询引出约定变更回流主控四条路径。
- 咨询记录可被查询，且不产生版本号；`Binding=true` 的记录可被门禁接受为依据，L1 记录被拒绝。
- 分类校验：场景卡集上的分类准确率可复现；L1 记录被引用的次数为 0。
- 前置：L2 触发率测试（§15.7）先于层级编号定稿完成。

## 16. 术语表

| 术语 | 含义 |
|---|---|
| 决策一致性协议（DCP） | 本文档所述协议。原名"会议协议"，"会议"降为 L4 级动作名保留 |
| 宿主 | 承载多 Agent 的运行环境。本文不绑定任何具体宿主 |
| 执行层 | 宿主中真正执行写类操作的那一层；版本硬门禁落在这里 |
| 安全点 | 一次工具调用返回之后、下一次工具调用发起之前 |
| Worker | 执行具体任务、可能发起升级请求的 Agent |
| 主控 | 单一协调点：受理升级、定序、维护决策日志与版本、组织 L4 会议 |
| 决策者 | 真正作出裁决的角色，可为人或 Agent；与常驻仲裁服务解耦 |
| 五级升级 | 升级阶梯 L0–L4，按**承诺强度**排序：L0 自决（无需外部信息、无承诺）；L1 信息（需要事实但不产生承诺，记录不可引用）；L2 单点承诺（责任域 owner 作出可被依赖的确认，记录可引用、不递增版本）；L3 全局约定（改变所有相关 Worker 必须遵守的约定，版本化 + 广播）；L4 多方决议（无唯一 owner / 互斥方案 / 争议，会议）。定义见 §2 |
| 信息（L1） | 不产生承诺的答复；可由记录、主控、用户或知情者给出；记录标 `Binding=false`、`Citable=false`，不得作为写依据。见 §2.2、§15.1 |
| 定向咨询（L2） | 单点承诺的获取过程：主控配对后，问题方与责任域 owner 双向问答；owner 作出可被依赖的确认；落咨询记录、不递增版本；`Binding=true` 时可作为写依据。见 §15 |
| 承诺 | 可被他人依赖、并作为后续行为依据的答复或决定；按约束范围分 L2 单点、L3 全局、L4 多方。见 §2 |
| 可引用性 | 一条记录能否作为写操作依据的属性；只有 `Binding=true` 的 L2 记录与当前有效的 L3/L4 决议可引用，L1 记录一律不可引用。见 §2.2 |
| 重分类 | 答复时把议题从 L1 升为 L2、或从 L2 升为 L3（也可反向降级）的动作，须留 `ReclassifiedFrom` 与理由。见 §2.2、§15.4 |
| 责任人登记（Ownership Registry） | 主控在派生 Worker 时登记其责任范围（模块 / 接口 / 文件）；为 L2 提供承诺主体与路由、去重、L4 参会者筛选、Agent 级并行写分片与门禁跨域判定提供依据。见 §15.2 |
| 人控模式 | 人类介入深度轴上"拉满"的档位：用户直接扮演主控 / 决策者。主控 Agent 的基础形态。见 §13.8 |
| 仲裁服务 | 常驻宿主的机制进程，持有决策日志、责任人登记、升级请求队列、单点接收序号、会议状态机；与可替换的"主控角色 / 决策者"解耦。见 §13.8 |
| 秘书 Agent（Secretary） | 任务组的结构生成与记录角色：生成拆分方案、创建 Worker 并登记责任域、全程记录与转发；不持有责任域，因而不能作为 L2 的承诺主体。旧称"分析 Agent"作废。见 §13.8 |

## 17. 宿主能力要求（实现无关）

协议不规定语言、框架、存储与传输，但要求宿主至少提供以下能力。编号用于实现指南中的对照。

| 编号 | 能力 | 要求 |
|---|---|---|
| R1 | 单点受理与定序 | 一个协调点持有升级请求队列、当前会议引用与单调递增的接收序号（或逻辑等价的串行化机制） |
| R2 | 安全点 | Agent 循环能在两次工具调用之间检查协调消息；不得中断进行中的操作 |
| R3 | 可拦截的写路径 | 所有写类动作经过统一执行入口；执行层能从**运行时注入**的调用者上下文中读到 `TopicKey`、依据版本、依据记录 ID，模型无法伪造或修改该上下文 |
| R4 | 持久化审计存储 | 决议、咨询记录、依据留痕、去重复用依据可追加写入，并可按议题 / Agent / 时间查询 |
| R5 | 消息投递 | 至少支持点对点（咨询问答）与广播（结论订阅）；不要求消息顺序，版本门禁负责兜底 |
| R6 | 待答队列 | 会议审批、L1 提问、L2 咨询知会、决议审核、危险操作确认统一入队；人控模式下应支持跨重启恢复 |
| R7 | 责任人登记 | 派生 Worker 时登记责任域；可查询当前 owner；Worker 回收后历史保留 |
| R8 | 时间源与超时 | 可注入时钟；支持审批（默认 120 秒）、会合（默认 60 秒）与咨询超时 |
| R9 | 决策日志单写者 | 版本递增与广播只能由协调者在串行上下文中执行，避免并发写导致版本回退或跳号 |

**最小合规档位**（供实现者取舍）：

| 档位 | 内容 |
|---|---|
| 核心（Core） | L0–L3 + 决策日志 + 版本硬门禁 + R1–R5、R8、R9 |
| 标准（Standard） | 核心 + L2 定向咨询 + R6、R7 |
| 完整（Full） | 标准 + L4 会议 + §13 人类介入深度轴（开关 A/B、断路器、人控模式） |

若宿主不满足 R3（存在绕过写路径），仍可实现记录与流程，但**不得声称**"版本门禁绕不过去"，只能声称"覆盖统一执行入口的写操作"。

# DCP 设计论证与已知边界

> 配套文档：[规范](specification.md) · [实现指南](implementation-guide.md)
> 目的：记录"为什么这样设计"、协议**不能**保证什么，以及评估协议所需的指标口径。规范描述"是什么"，本文描述"为什么"与"边界"。

---

## 1. 问题：并行 Agent 的认知漂移

多个 Agent 并行工作时，典型失效模式不是"某个 Agent 算错了"，而是：

| 失效模式 | 例子 |
|---|---|
| 陈旧读 | A 依据 v3 的接口约定写代码，而 B 已经把约定改成 v4 |
| 片面信息 | A 以为某模块返回 null，B 实际改成抛异常 |
| 私下一致 | A 与 B 口头（消息里）约定了一个字段语义，第三个 Worker C 完全不知道 |
| 重复决策 | 同一议题被不同 Worker 反复提出、反复讨论 |

把这些都拿去开会可以解决一部分，但会带来两个新问题：**成本**（每次会议都要模型时间与 token）与**延迟**（Worker 在等会议时无法工作）。而且真实项目中大多数问题根本不需要多方参与。

DCP 的取舍是：**用分级把"不需要协调"的问题挡在会议之外，用硬门禁把"必须一致"的问题变成绕不过去的检查。**

---

## 2. 为什么排序轴是"承诺强度"而不是"影响范围"

早期版本用"是否影响其他 Worker"作为判据，但这条判据有两个问题：

1. **不可观测**：一个答案是否影响别人，往往在答案产生之后才知道。提问者无法在升级时客观回答；
2. **无法检验**：判错了不会留下任何可检查的痕迹——主控说"这只是局部问题"，就真的没有任何机制反驳它。

改成"承诺强度"后，判据变成**"这个答复会不会被写进代码 / 文档，成为别人以后要依赖或遵守的东西"**。这条：

- 提问者在写代码 / 文档时自己就知道答案；
- 能落到记录字段（`Binding` / `Citable`）上；
- 能在门禁上执行（引用 L1 记录 = 拒绝）。

代价是判定点从"一个二分"变成"四问"，误判面变宽（§4）。这是有意识的交换：**用更宽的误判面，换一个可执行的边界**。

---

## 3. 为什么门禁必须在代码路径上

如果只在系统提示词里写"记得检查决议版本"，模型完全可以不检查就写入。这样协议的核心主张（防止基于过时决议的写）就退化成"建议"。

因此 DCP 要求：

1. 依据版本由**运行时注入**的调用者上下文携带，模型无法修改；
2. 所有写类操作在**统一执行入口**拦截；
3. 拒绝时把差异回灌，要求重新对齐。

这是分布式系统中防"陈旧读"的标准做法：广播可能漏（Worker 正在跑长命令），但代码级拦截不会漏。

**但必须如实声明边界**：若宿主的写路径存在绕过入口（直接调底层 API、动态构造命令、按全路径启动进程等），门禁只能算政策守卫，不是安全边界。这一条同时写进了规范 §11.2 与 §17。

## 4. 可引用性：把分类错误变成可计数事件

L1（信息）与 L2（承诺）的差别如果只停留在"问了谁"，判错就没有后果。可引用性把差别落到检查上：

| 误判 | 是否可发现 | 后果 |
|---|---|---|
| L1 → L2（保守多问） | 可观察 | 成本增加，不产生漂移 |
| L2 → L1（少问一次） | 被引用时可发现 | 门禁拒绝该写操作 |
| **L3 → L2** | **不可发现** | 承诺记录可引用、又不广播，受影响方不知道约定变了 |
| L3 → L1 | 部分可发现 | 被引用时拒绝，但约定仍未广播 |
| L3 → L4（保守开会） | 可观察 | 成本增加 |

**最大的残余盲区是 L3 → L2**：它既不触发广播，也不触发版本递增，门禁对"没有版本号的误判"无感。协议不宣称这个问题已解决，只提供事后审计（L1 / L2 都留记录）与判定权下放（提问者可申请升级）来降低概率。

这也是为什么 §13 的免审开关必须等审计数据完备后才能打开：默认状态下人还在回路里，L3 → L2 的漏判仍可能被人发现；开关打开后人退出回路，这类误判将完全无人察觉。

## 5. 指标口径

DCP 的价值不能靠"我觉得更好"来论证。以下指标可在运行中直接统计，**不需要对照组实验**。

### 5.1 核心指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 认知漂移事件数 | **因依据陈旧决议而被迫重新对齐并重做**的次数。不含被门禁拦截阻止的错误——那属于拦截成功，不计入漂移 | 结果指标；也是信任授权的"返工"门槛输入 |
| 门禁拦截次数 | 写类操作因依据版本过期或依据类型不合格被拒绝的次数 | 机制在触发的**直接证据**；每次拦截即一次被阻止的过期写 |
| 拦截后重对齐成功率 | 被拦截后，该 Agent 重新对齐并成功重试的比例 | 衡量门禁是在纠偏，还是只在制造摩擦 |
| 漏网事件数 | 写通过了门禁，但事后被证明其依据已过期（例如该决议事后被推翻）的次数 | 门禁的**失效面**，需事后审计才能发现 |
| 升级触发分布 | 按 L0–L4 分桶的升级次数 | 观察阶梯是否真的把成本压到了低层级 |
| 分类重分类率 | 答复时由 L1 升 L2、L2 升 L3 等的比例 | 衡量判定树的可操作性；也是 L2 触发率测试的数据 |

### 5.2 为什么不用"拦截率"

设 `拦截率 = 拦截次数 ÷ 本应拦截的写操作总数`。这个比值**同义反复**：

一次写能通过门禁，前提就是其依据版本等于当前版本；被拦下的写，"本应拦截"必然为真。于是分母恒等于分子，比值恒为 1。它与"漂移数恒为 0"是同一类错误：用定义造出一个没有信息量的漂亮数字。

**影子判定只在门禁可被旁路时才有对照意义**：当免审开关打开、或某条写路径绕过门禁时，"依据状态"仍被记录，此时记录与判定分离，才构成真正的反事实（"若门禁不在，会有多少过期写通过"）。硬门禁始终开启时，只产出拦截事实，不产出反事实。

### 5.3 描述性统计：依据状态分布

把全部写类操作按提交时刻的依据状态分桶：

- `absent`（无依据）
- `stale`（依据过期）
- `current`（依据最新）

它回答"写的依据来自哪里"，**不回答**"门禁拦住了多少"。不要把它包装成比值。

### 5.4 如何回答"漂移数为 0 是否说明机制没用"

用三个量回答，而不是用漂移数：

1. **拦截次数**：证明机制在触发，给出"防止的漂移下界"；
2. **重对齐成功率**：证明拦截后能纠偏，而不是制造摩擦；
3. **漏网事件数**：暴露失效面。

如果三者都是 0（从未拦截、从未漏网），说明样本里根本没有"依据会过期"的场景，此时应当如实说"该场景下无法评估"，而不是宣称协议有效。

## 6. 去重的盲区

相同议题去重是成本护栏的一部分，但它与分类误判同构：

- 相似性判定由主控单方做出；
- 不产生新版本；
- 误判时会复用不相关决议，而复用的版本号本身合法，门禁无感；
- 去重是优化动作，通常不会被怀疑，因此比分类误判更隐蔽。

**缓解措施**：复用决议时必须落一条复用依据（被复用决议 ID + 判定理由），与咨询记录同处存放，使复用可事后审计。即便如此，复用的正确性仍无法自动验证。

## 7. L2 的前置测试：先测再做

L2（单点承诺）是暂定层级。它的风险与 L4 一样：**可能长期触发率接近 0**。因此在实现 L2 之前，先做触发率测试。

### 7.1 方法

从真实开发对话中取 20–30 个"当时不知道该问谁"的问题，做成场景卡（规范 §2.3 是种子集），逐张标注：

- 分类（L0/L1/L2/L3/L4）；
- `Binding`（是否产生可被依赖的承诺）；
- `OwnerId`（责任域 owner 是否存在）；
- 是否会被后续写操作引用。

### 7.2 判断

统计三件事：

1. L1 / L2 各自占比；
2. L2 中 `Binding=true` 的比例——**若接近 0，说明 L2 只承载事实转交**；
3. L1 记录被引用为写依据的次数——**应为 0**；非 0 即分类错误。

若第 2 项接近 0，按规范 §2.4 把 L1/L2 合并为一级咨询（`Binding` 字段区分），编号收缩为 L0–L3。**收缩不是删除**：可引用性这条治理边界仍然保留，只是从"层级"变成"字段"。

### 7.3 为什么不能跳过

编号与文档措辞一旦按五级定稿，收缩就要改两遍号（L2 → 合并、L4 → L3），且会波及术语表、指标分桶与实现契约。测试必须排在编号定稿之前。

## 8. 人类介入深度轴

DCP 把"人类介入到什么程度"表述为一条轴，而不是若干并列开关：

| 档位 | 内容 |
|---|---|
| 默认 | 批准开会 + 审核决议，人都在回路 |
| 开关 A 打开 | 免"批准开会" |
| 开关 B 打开 | 免"事后审核" |
| 断路器触发 | 自动关闭开关 B（不关闭 A） |
| 人控模式 | 用户直接扮演主控 / 决策者（"拉满"） |

三条设计取向：

1. **只由人放权，不由数据自动放权**：系统只能给"建议放开 / 暂不建议"，开关必须由人显式打开；
2. **收回可以自动，但只收回开关 B**：严重否决与返工都是"决议质量"信号，语义上只指向事后审核；开关 A 没有自动收回路径，只能由人手动关；
3. **人控模式是基础形态而非可选扩展**：主控先按"决策者可以是人"构建，Agent 自主裁决是后续升级路径。这样验收风险最低，也把协议里最难验证的部分（模型仲裁能力）换成了最可靠的部分（人）。

## 9. 落地顺序建议

不建议一次性实现全部五级。推荐顺序：

| 阶段 | 内容 | 理由 |
|---|---|---|
| 1 | L0–L3 + 决策日志 + 版本硬门禁 + 结论订阅 | 每天真在跑、也真能进指标的部分 |
| 2 | L2 定向咨询 + 责任人登记 | 先做触发率测试；上线后观察 L4 剩余触发率 |
| 3 | L4 会议 | 成本最高；一次完整的人机会议即可验证机制，不必追求高频 |
| 4 | 人类介入深度轴（开关 A/B、断路器、人控模式） | 依赖前面阶段的审计数据 |

**L4 的定位**：如果 L2 落地后 L4 触发率长期为 0，应据实把 L4 定位为前瞻 / 演示能力，而不是继续追加投入。这不是缺陷——协议的日常价值主要来自低层级与门禁。

## 10. 反模式

| 反模式 | 为什么错 |
|---|---|
| 把 DCP 当共识算法 | 它不解决多主节点日志一致；单一协调点是前提 |
| 把版本门禁当安全边界 | 它是政策守卫；绕过统一执行入口即可失效 |
| 用提示词代替门禁 | 模型可以忽略提示词，"绕不过去"就不成立 |
| 所有问题都升级到 L4 | 成本失控；白名单存在的意义就是挡掉这类升级 |
| 用全局通过率决定放开开关 | 简单议题拉高数字，掩盖复杂议题的低通过率 |
| 让 Worker 自行递增版本 | 破坏决策日志的单写者与全序 |
| 允许咨询嵌套 | 等待图可能出现环；1:1 + 非阻塞 + 禁止嵌套是防成环的前提 |
| 认为"漂移数为 0"就是成功 | 也可能是从未触发；必须结合拦截次数与漏网事件数 |

## 11. 开放问题

| # | 问题 | 当前处理 |
|---|---|---|
| 1 | L2 应答超时的建议值 | 在模拟环境中调参，不用真机试错 |
| 2 | 责任人登记与角色系统的耦合方式（角色默认责任域 vs 派发时显式指定） | 由宿主决定；协议只要求"派生 Worker 时登记" |
| 3 | L2 引出约定变更的判定由谁做（提问方 / 责任人 / 主控） | 倾向主控，避免责任人与提问方私下扩大结论 |
| 4 | L2 落地后 L4 的实际触发率 | 观察后再决定 L4 是否永久降为前瞻能力 |
| 5 | 每次写都记录依据状态对性能的影响 | 实测量级，必要时采样 |
| 6 | L2 与 L3 之间的成本倒挂是否需要专门说明 | 需要；报告中据实陈述 |
| 7 | 人控模式下待答队列跨重启恢复的最小范围 | 至少覆盖 L1 提问、L3 裁决、L4 会议请求 |
| 8 | "人类介入深度"在界面上如何呈现（滑杆 / 预设组合 / 枚举） | 由宿主决定 |
| 9 | 分层判定树在真实场景中的准确率 | 用场景卡集评估；可复现才算通过 |

## 12. 效度威胁（如实声明）

- **样本量**：协议目前主要由单作者在个人项目中设计、以模拟 Agent 验证；缺少多团队、长周期的真实部署数据。
- **L4 触发率可能为 0**：在 1–2 个 Worker 的场景下，多方会议可能几乎不触发。这不能证明会议机制无效，只能说明该场景用不到它。
- **指标依赖门禁覆盖率**：若宿主存在绕过写路径，"拦截次数"只覆盖统一入口，不能外推为"防止了多少漂移"。
- **人工审核数据的主观性**：通过率、严重否决分级都依赖审核者判断；单人或小样本下容易失真。
- **未覆盖恶意节点**：协议假设参与者合作，不提供拜占庭容错。

## 13. 与来源项目的关系

本协议最初在作者的个人 AI coding harness 项目中提出并迭代。独立化整理时做了三类修改：

1. **剥离宿主实现细节**：原文档中的工具层、UI、存储、进程与传输方案不再属于协议，改写为宿主能力要求（规范 §17）；
2. **解除文档耦合**：原文对 harness 内部文档的交叉引用改为本仓库内的自包含说明；
3. **补齐协议自身的边界**：新增范围、假设、非目标与效度威胁，明确 DCP 不是共识算法、不是安全边界，也不宣称解决 L3 → L2 漏判。

协议机制（五级阶梯、可引用性、决策日志与版本门禁、L2 定向咨询、人类介入轴）保持不变。
